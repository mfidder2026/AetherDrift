# M0 — Haalbaarheid en metingen

Datum: 2026-10-26 · Machine: Apple M3 Max, 128 GB, macOS 27.0.1 · MLX 0.32.4, mlx-lm 0.32.2

## 1. SSD-snelheid

Volledige tabel: [2026-10-26-M0-ssd.md](2026-10-26-M0-ssd.md) (gemaakt met `bench/ssd.py`).

| | Resultaat |
|---|---|
| Sequentieel lezen, maximum | **6,77 GB/s** |
| Random lezen (16 KB-aligned), maximum | **6,84 GB/s** |
| Verzadiging | Bij blokken van 1 MB al vanaf queue depth 4 |
| Queue depth 1 | 3,4 GB/s (1 MB) tot 6,5 GB/s (64 MB) |
| mmap + madvise (16 MB, kopie eruit) | 3,23 GB/s |
| Schrijven (F_NOCACHE) | 6,70 GB/s |

Conclusies:
- Random lezen is even snel als sequentieel, zolang de blokken ≥ 1 MB zijn en er ≥ 4 verzoeken tegelijk lopen. Parallelle reads zijn dus essentieel; de volgorde op schijf niet.
- pread + F_NOCACHE is 2× sneller dan mmap → ADR-002.
- Repack levert voor units ≥ 1 MB geen meetbare winst op → ADR-003.

## 2. Referentiemodel GLM 5.3

Geverifieerd via de Hugging Face-API (alleen config en safetensors-headers, geen download).

| | `mlx-community/GLM-5.3-4bit` |
|---|---|
| Grootte op schijf | **418,3 GB** (91 shards) — niet ~150 GB zoals in v1 aangenomen |
| Architectuur | `glm_moe_dsa` (MoE + MLA-attention + sparse attention-indexer) |
| Lagen | 78, waarvan 3 dense (0–2) en 75 MoE (3–77) |
| Experts | 256 routed per laag, 8 actief per token, plus 1 shared expert |
| mlx-lm-ondersteuning | Ja: `mlx_lm/models/glm_moe_dsa.py` |

Verdeling van de gewichten:

| Deel | Grootte | Plaats in Drift-MoE |
|---|---|---|
| Embeddings, lm_head, norm | 1,1 GB | Altijd in RAM |
| Kern per laag (attention, router, shared expert, dense MLP's) | 9,6 GB | Altijd in RAM |
| Routed experts | 407,7 GB | Expert-cache |
| **Per expert** | **21,2 MB** in 9 tensors (3 × 6,3 MB gewichten + 6 × 0,39 MB scales/biases) | Eén unit |

Experts staan gestapeld per laag (`switch_mlp.*.weight` met shape `[256, …]`), zoals verwacht in §6.3: één expert is een aaneengesloten slice op as 0.

Ook beschikbaar: `mlx-community/GLM-5.3-Flash-4bit` (204 GB, `glm5_next`, multimodaal). Dit type wordt **niet** door mlx-lm 0.32.2 ondersteund.

## 3. Verwachting voor GLM 5.3 Q4 op 128 GB

- Expertdata per token: 75 × 8 × 21,2 MB = **12,7 GB**.
- Gewichtenbudget: min(128 − 16, 115 werksetlimiet) − 8 KV − 2 overhead ≈ 102 GB. Daarvan is 10,7 GB vast, dus er blijft ≈ 91 GB over voor de expert-cache: **~22 % van alle experts**.
- Bij 6,7 GB/s:

| Hitrate | GB van SSD per token | Tok/s (I/O-grens) |
|---|---|---|
| 0 % | 12,7 | 0,53 |
| 50 % | 6,4 | 1,05 |
| 70 % | 3,8 | 1,76 |
| 85 % | 1,9 | 3,5 |

De hitrate hangt af van hoe scheef de routering in de praktijk is. Dat moet in M4 gemeten worden met echte prompts. Een realistische verwachting is **0,5–2 tok/s**. Het werkt dus, maar het is niet snel. Dit moet de app vooraf eerlijk tonen.

## 4. MLX-geheugen-API's (MLX 0.32.4)

- Top-level in `mx`: `set_memory_limit`, `set_cache_limit`, `set_wired_limit`, `get_active_memory`, `get_cache_memory`, `get_peak_memory`. Er zijn ook (oudere) aliassen onder `mx.metal`.
- `mx.device_info()`: `max_recommended_working_set_size` = **115,4 GB** op deze machine (van de 128 GB); `max_buffer_length` = 86,6 GB.

## 5. Nog open (naar M3/M4)

- Of geheugen na eviction echt vrijkomt met een lage `set_cache_limit`: meten in de Drift-spike.
- Expert-slots zonder volledige kopie (§6.6): meten in M4.
- Kleine reads (0,39 MB scales/biases) per expert: per laag alle reads tegelijk indienen zodat de queue depth hoog blijft.
